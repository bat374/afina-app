# Порядок обновления «Афины»

## Два канала доставки изменений

**OTA (автоматически, через `expo-updates`)** — для любых правок в JS/TS-коде
и ассетах. Не требует установки нового APK. После `git push` в `main`
GitHub Actions сам публикует обновление, и оно приходит на уже
установленные телефоны.

**Новый APK (вручную)** — обязателен только если:
- добавилась/удалилась нативная зависимость (новый пакет с нативным кодом);
- изменились нативные настройки в `app.json` (permissions, плагины и т.п.);
- пришлось поднять `runtimeVersion` в `app.json`.

Во всех остальных случаях достаточно OTA.

## Обычный порядок (JS/TS-правка, без нового APK)

1. Внести правки в код.
2. `pnpm typecheck` и `pnpm exec expo export --platform android` — должны
   пройти чисто.
3. Если менялась схема БД (новая колонка/таблица) — **сначала** применить
   SQL-миграцию в Supabase (SQL Editor), **и только потом** пушить код.
   Порядок именно такой: аддитивная миграция безопасна для старого кода
   (он её просто не видит), а вот если код уйдёт раньше и начнёт
   ссылаться на ещё не существующую колонку — синхронизация упадёт у всех
   пользователей сразу.
4. Закоммитить и запушить в `main`.
5. GitHub Actions сам: соберёт APK (на всякий случай) и опубликует
   OTA-обновление в канал `production`.
6. Проверить, что публикация прошла: `gh run list --repo bat374/afina-app --limit 1`,
   в логе шага «Publish OTA update» должно быть `✔ Published!`.
7. На телефоне: обновление скачивается в фоне при следующем запуске, но
   **применяется только при следующем полном перезапуске** — то есть
   нужно открыть приложение дважды. На этом телефоне (MIUI) обычного
   сворачивания недостаточно — MIUI глушит фоновую проверку обновлений.
   Рабочая последовательность:
   **Настройки → Приложения → Афина → Остановить** → открыть → подождать
   ~10 секунд → **Остановить** ещё раз → открыть снова.

## Если нужен новый APK (нативные изменения)

1. Всё то же самое (typecheck, export, миграция при необходимости, пуш).
2. Если добавилась/удалилась нативная зависимость — обязательно поднять
   `runtimeVersion` в `app.json` (иначе `eas update` откажется
   публиковать, а старые OTA-обновления по ошибке могут показаться
   совместимыми с несовместимым нативным кодом).
3. Дождаться сборки в GitHub Actions (вкладка **Actions** в репозитории →
   workflow **Build Android APK**) — обычно 7–8 минут.
4. Скачать артефакт `afina-apk` (Artifacts на странице прогона) и
   установить на телефон. Сборка подписана настоящим EAS-keystore
   (через `eas build --local` в CI, использует `EXPO_TOKEN`), поэтому
   встаёт как обычное обновление поверх старого приложения — данные не
   теряются.
5. Если скачивание из GitHub не идёт (бывает при плохой сети) — попросить
   Клода скачать файл на компьютер и раздать по локальной сети
   (`python3 -m http.server` + IP компьютера в той же Wi-Fi-сети, что и
   телефон).

## Нужные секреты в GitHub (Settings → Secrets and variables → Actions)

- `EXPO_PUBLIC_SUPABASE_URL` — URL проекта Supabase.
- `EXPO_PUBLIC_SUPABASE_ANON_KEY` — Publishable key (`sb_publishable_...`)
  из Supabase, **не** secret key.
- `EXPO_TOKEN` — токен доступа с expo.dev (Account settings → Access
  tokens), используется и для сборки (получение keystore), и для
  публикации OTA.

## Проверка, что данные точно синхронизированы

SQL в Supabase (SQL Editor):

```sql
select
  (select migration_completed_at from user_settings limit 1) as last_sync,
  (select count(*) from accounts) as accounts_count,
  (select count(*) from operations) as operations_count,
  (select count(*) from debts) as debts_count,
  (select count(*) from scheduled_flows) as scheduled_flows_count,
  (select count(*) from budgets) as budgets_count,
  (select count(*) from financial_goals) as goals_count;
```

`last_sync` должен быть свежим, а счётчики — совпадать на глаз с тем, что
видно в приложении.

## Известные ограничения

- OTA работает только пока `runtimeVersion` в приложении совпадает с тем,
  что был при публикации обновления (сейчас `"1.2.1"`, фиксированная
  строка — политика `appVersion` не поддерживается в текущей схеме сборки).
- Полный (не инкрементальный) full-snapshot sync между двумя одновременно
  активными устройствами теоретически может привести к перезаписи данных
  «последним записавшим» — задокументировано отдельно, не исправлено в
  рамках уже сделанных правок (требует более крупного рефакторинга
  протокола синхронизации).
